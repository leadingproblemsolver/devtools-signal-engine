External repository investigation

sqlite-utils #841 — reproduction + source localization

Python 3.11sqlite-utils 3.36.0branch: main

Reported behavior

rows_where() and delete_where() tolerate a missing table, while count_where() raises sqlite3.OperationalError.

Upstream issue #841

Reproduction

python -c "import sqlite_utils; db=sqlite_utils.Database(memory=True); print(list(db.table('does_not_exist').rows_where())); db.table('does_not_exist').delete_where()"

Observed: []; delete_where() completes silently.

python -c "import sqlite_utils; db=sqlite_utils.Database(memory=True); print(db.table('does_not_exist').count_where())"

Observed: sqlite3.OperationalError: no such table: does_not_exist.

Source localization

MethodPathWhy behavior differs
rows_where()sqlite_utils/db.py
SELECT <select> FROM [<table>] WHERE <where>		Implemented as a generator; SQL execution is deferred until iteration.
delete_where()sqlite_utils/db.py
DELETE FROM [<table>] WHERE <where>		Guards with if not self.exists(): return self, silently returning the Table object.
count_where()sqlite_utils/db.py
SELECT count(*) FROM [<table>] WHERE <where>		Executes synchronously via self.db.execute(), so SQLite immediately raises for the missing table.

Root-cause hypothesis

Missing-table semantics are inconsistent across Table methods because lazy generator evaluation, explicit existence guards, and eager scalar execution use different failure behaviors.

Constraint

The maintainer explicitly deferred normalizing this behavior to v5 because changing it would be a breaking compatibility change. This investigation does not claim a patch or merged contribution.
